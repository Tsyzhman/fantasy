# FEAT-007: Telegram-помощник перед дедлайном {#root}

## Простыми словами {#plain-language}

Пользователь связывает профиль Fantasy Scout с личным чатом бота. В день дедлайна получает отдельное сообщение по каждому турниру: кого проверить в составе, у кого ALT=0 или бланк, когда играют команды, что опубликовано о популярных игроках. Обычное время начала рассылки — 09:00 МСК. Бот показывает, какой именно состав и насколько свежие данные он проверил.

## Цель {#goal}

Дать пользователю своевременный проверяемый список рисков своего состава на конкретный дедлайн без ручного обхода источников.

## Управляющие документы {#governing-specs}

Legacy product canon: `specs/common/main.md`; ограничения UI из `AGENTS.md` сохраняются. Runtime: `spec://modules/telegram/INFRA-005-deadline-pipeline#root`. Популярность: `spec://modules/machete/FEAT-006-sports-popularity#root`. Прогноз основы: `spec://modules/machete/INFRA-004-sorareinside-starters#root`.

## Границы {#scope}

Входит: привязка, настройки подписки по Sports-турнирам, утренний отчёт, отключение. Не входит: смена сайта на Telegram-only auth, автоматические замены, чтение Sports cookies сервером, обход приватности, гарантированная доставка всем в одну секунду. Первая область — футбольные Sports-турниры; КХЛ требует отдельного адаптера по своим спекам, не получает футбольные правила автоматически.

## Участники и запуск {#actors}

Авторизованный пользователь сайта, владелец Telegram-аккаунта в private chat, webhook или long polling через VPN relay, scheduler и delivery worker. Привязка инициируется пользователем в настройках. Рассылка разрешена только после согласия, выбора турниров и запуска бота самим пользователем. Связь с Telegram не подтверждает владение введённым публичным Sports profile ID.

## Привязка и код каждые 15 секунд {#linking}

### Основной сценарий {#scenarios}

1. Настройки → «Подключить Telegram»: создать одну короткую link session для пользователя. Показать кнопку «Открыть бота», одноразовый код и обратный отсчёт; не менять существующий вход на сайт.
2. Код меняется каждые 15 секунд только пока открыт этот блок и вкладка видима. Закрытие вкладки/блока прекращает обновления. На стороне сервера нет миллиона постоянных таймеров и предварительной генерации кодов всем аккаунтам.
3. Предлагаемый ручной код — 12 случайных символов Crockford Base32 (60 бит), группами `XXXX-XXXX-XXXX`. Уникальный индекс на digest активного кода, коллизию перевыпустить. Кнопка использует отдельный случайный 128-битный base64url secret в `https://t.me/<bot>?start=<secret>` для того же challenge. Это проектные параметры, не существующие endpoints.
4. В БД хранить только HMAC/digest секретов, userId, linkSessionId, slot, expiresAt, consumedAt. 15 секунд основной жизни + не более 15 секунд grace для предыдущего кода. Серверное время авторитетно. Один slot выдаётся идемпотентно; несколько вкладок используют одну сессию. Сессия истекает через 10 минут, затем требуется явное повторное открытие.
5. Пользователь нажимает Start или отправляет код в private chat. Одна атомарная транзакция потребляет challenge и оба его способа ввода; повтор/гонка не создают вторую привязку. Telegram identity берётся из `message.from.id`, chat — из проверенного private update, не из username или параметров клиента.
6. Бот отвечает фиксированным текстом без AI: `/start` без payload даёт приветствие и просит код; введённый код получает результат «подошёл/не подошёл», при успехе бот называет аккаунт (email) и просит подтверждение на сайте. Конфликт чужого Telegram не раскрывает чужой аккаунт. Rate limits и durable inbox сохраняются.
7. На сайте показать кандидата Telegram (имя/username при наличии и часть стабильного ID) и кнопку подтверждения. Привязка и подписка активируются только после подтверждения в исходной session auth. До него бот не отправляет состав. Pending candidate истекает через 2 минуты; это предотвращает незаметную привязку чужого Telegram по перехваченному коду.
7. Успех: код скрывается, показаны подключённый аккаунт, турниры, время рассылки, кнопки паузы/отвязки. В боте — подтверждение. Привязка не выдаёт сессионную cookie сайта и не является восстановлением пароля.

При переходе в pending атомарно закрыть остальные challenge этой link session и остановить выдачу новых кодов. Одна session имеет только одного кандидата; повторное предъявление другого slot не заменяет его. Отмена кандидата в авторизованном профиле отзывает всю session и позволяет создать новую.

Начальные ограничения: выпуск кода максимум один на slot и 6 запросов/мин на user; ввод максимум 5 неуспешных попыток/мин на Telegram ID, 20/час, с общим bot limiter; подтверждение 5 попыток/мин на user/session. Общие IP-лимиты для site API дополняют, а не заменяют user-limits. Rate limits атомарные и общие между репликами. Ошибка кода не раскрывает наличие user. Коды и deep links исключены из аналитики, access logs и error traces; ответы `Cache-Control: no-store`, отсутствуют сторонние ресурсы, `Referrer-Policy: no-referrer`. POST-операции защищаются существующей session auth, Origin/CSRF.

REVIEW: 15 секунд неудобны для ручного ввода, поэтому кнопка — основной путь; fallback с grace сохраняет запрошенную ротацию. Шестизначный код без отдельного challenge ID не подходит для поиска по общей базе миллиона пользователей. Более длинное окно возможно только как отдельное продуктовое решение.

## Состояния и настройки {#data}

| Сущность | Состояние/инвариант |
|---|---|
| TelegramLink | userId UNIQUE; telegramUserId UNIQUE; chatId; PENDING/ACTIVE/PAUSED/BLOCKED/REVOKED; consentAt, linkVersion; ID хранить в bigint/decimal string |
| TelegramLinkSession/Challenge | slot, secret digests, expiry, consumedAt; одна открытая session на user; purge после срока |
| TelegramSubscription | UNIQUE(userId, contestId); providerSquadId/выбранный локальный squadId, enabled, sourcePreference |
| Report | userId, contestId, season, providerRoundId, reportVersion, данные snapshot/source/freshness; immutable версия |

Один аккаунт сайта ↔ один Telegram-аккаунт в первой версии. Конфликт требует явной отвязки с действующей авторизацией, автоматическая перезапись чужой связи запрещена. Повтор `/start` для действующей связи не создаёт подписку заново. `/stop` сразу ставит PAUSED и отменяет ожидающую рассылку, `/start` сам по себе паузу не снимает: предложить кнопку «Возобновить». `/unlink` после подтверждения в том же private chat отзывает связь и pending jobs. Удаление аккаунта сайта отзывает связь; повторная привязка использует новую linkVersion. Перед каждой отправкой worker заново проверяет состояние и consent.

Если один Sports-профиль имеет несколько команд одного турнира, пользователь выбирает нужную; нельзя выбирать случайную «последнюю» команду. Несколько турниров подписываются независимо. `/settings`, `/help`, `/status` доступны без массовой повторной отправки отчётов.

## Какой состав проверяет бот {#squad-source}

Требование 08:00 означает импорт последнего **доступного опубликованного** Sports состава. Текущий анонимный API не гарантирует доступ к изменениям открытого тура; UI проекта прямо предупреждает об этом, текущий background snapshot рассчитан на публикацию после начала тура. Этот scheduler нельзя просто перенести на 08:00.

Отдельный утренний refresh сохраняет notification input, не перезаписывает планы пользователя. Обязательные поля: source (`SPORTS_PUBLISHED` / `SITE_SAVED` / будущий `EXTENSION_CONFIRMED`), sourceTourId, targetTourId, providerSquadId, fetchedAt, sourceUpdatedAt если известен, selections, mappingCoverage. Время скачивания не означает время последнего изменения состава.

- По умолчанию подписка на Sports использует SPORTS_PUBLISHED. Сообщение явно говорит «Опубликованный состав тура N, проверяем риски на тур N+1; последние замены до дедлайна недоступны».
- Пользователь может явно выбрать «Проверять сохранённый состав Scout». Он не называется подтверждённым Sports составом.
- Для действительно последних замен нужен дополнительный согласованный канал: расширение, читающее подтверждённый Sports состав в браузере авторизованного пользователя и передающее только состав на сайт, либо официальная интеграция. Существующее расширение переносит **из Scout в Sports** и обратного утреннего импорта сейчас не делает. Закрытый браузер не гарантирует синхронизацию в 08:00.
- Если ни одного подходящего снимка нет, сообщение сообщает причину и даёт кнопку настройки/состава. Ошибка импорта не обнуляет команду, неизвестные игроки не пропадают.

## Сигналы по игрокам {#signals}

Проверять всех игроков выбранного состава, выделяя основу, капитана/вице и скамейку пользователя. Это отличается от реального стартового XI клуба. ALT брать из того же текущего опубликованного расчёта и модели, что в Squad, для **целевого providerRoundId**, а не всегда из next-round index 0 или суммы горизонта.

| Условие | Текст и смысл |
|---|---|
| Расписание целевого тура полно, активных матчей клуба 0 | «Бланк: у команды нет матча в этом туре» |
| Проверенный прогноз XI относится к конкретному матчу этого тура, игрок вне XI | «Вне предполагаемой основы по SorareInside»; это прогноз, не официальный состав |
| Валидный неокруглённый ALT целевого тура равен 0 | «ALT 0 — проверьте игрока»; само по себе не доказательство отсутствия в старте |
| ALT отсутствует / маппинг неполон / прогноз старый / календарь неполон | «Нет надёжных данных» с причиной; не подменять нулём, бланком или зелёным статусом |
| Есть несколько условий | Один игрок, несколько причин; не дублировать строки |

В сообщении причины формулируются кратко: «вне прогноза основы SorareInside», «ALT 0», «прогноз основы устарел», «ALT недоступен». Префикс «Нет надёжных данных» не повторяется у каждого игрока; знак `?` и конкретная причина сохраняют неопределённость. Игроки с одинаковым полным набором причин объединяются в одну строку внутри основы или скамейки; отметки капитана и вице сохраняются рядом с именами.

В двойном туре учитывать все матчи: отсутствие в XI одного матча не означает пропуск всего тура. Ноль после округления, например 0,04 → 0,0, не равен настоящему нулю. При конфликте ALT и XI показывать оба сигнала. Глобальные галочки Sorare сейчас относятся к ближайшему матчу клуба, который может быть кубковым; применимость к отчёту проверять по fixture ID, клубам и kickoff, а не по одному `isStarter=false`.

## Сообщение и расписание {#message}

Отдельный отчёт на `(пользователь, турнир, сезон, providerRoundId)`, даже при совпавших дедлайнах. Порядок: тег и дедлайн → источник состава → риски основы/капитана → риски скамейки/unknown → расписание → популярность при наличии → кнопка Squad.

Опубликованные списки покупок и продаж включаются в сообщение отдельными блоками: до 10 игроков каждого списка в исходном порядке, со значением и единицей источника и ссылкой на статью. Официальные популярные трансферы Sports (`topTransferPlayers`) выводятся отдельным блоком только именем игрока и командой, без очков; расширенные секции роста/падения доли выбора в сообщение не выводятся. Доля выбора (ownership) остаётся в панели сайта и не выдаётся за покупки. Если статья не опубликована к срезу, блок опускается без выдуманных значений.

В сообщении нет времени обновления данных: подразумевается, что источники подгружаются перед отправкой, а состав Sports указывает только опубликованный тур. Технические статусы матчей (`NOT_STARTED`) не показываются.

Источник и предупреждение о последних заменах занимают одну строку. Причины, уже показанные у игроков, не повторяются отдельным сводным списком. Общие проблемы (например, отсутствующий состав или несопоставленные игроки) остаются отдельным кратким блоком и не сопровождаются утверждением, что рисков нет. Группы имён разбиваются по границе игрока при необходимости уложиться в лимит сообщения.

Пример с условными игроками и датами:

```text
#Англия10 · Дедлайн сегодня 18:30 МСК
Состав Sports: 9 тур (опубликованный). Последние замены на 10 тур могут отсутствовать.

Проверьте основу:
⚠ Игрок А (К) — вне прогноза основы SorareInside; ALT 0.
⛔ Игрок Б — нет матча в туре.
? Игрок В, Игрок Г (В) — прогноз основы устарел.

Матчи тура
Arsenal - Liverpool
Chelsea - Everton

Популярные трансферы Sports (топ-3):
1. Жилсон Беншимол, Акрон
2. Иван Обляков, ЦСКА

Популярные продажи Sports (топ-10):
1. Бруну Фернандеш, Португалия — -4,7%
2. Эрлинг Холанд, Норвегия — -4,6%
источник ↗

Открыть состав ↗
```

Расписание — строки **Команда 1 - Команда 2**. Telegram не поддерживает HTML `<table>`; строки экранируются, дата, время и статус не выводятся. Это компактный текст внутри сообщения, не требующий изображения на каждого пользователя.

Тег берётся из стабильного конфигурационного alias и номера Sports тура, не из локализованного заголовка: `england → Англия`, `championship → Чемпиошип` (точно как в запросе пользователя), `champions-league → ЛигаЧемпионов`. Примеры: `#Англия10`, `#Чемпиошип15`, `#ЛигаЧемпионов3`. Для остальных включённых турниров обязателен явный alias. Сезон, стадия и providerRoundId остаются внутренним ключом; в плей-офф заголовок содержит стадию, даже если хэштег повторяет порядковый номер.

Обычный отчёт укладывается в один `sendMessage` (до 4096 символов после разбора entities). Списки покупок и продаж включаются до 10 игроков; при превышении лимита первым сокращается необязательный блок популярности до ссылки, затем сообщение делится на детерминированные части `1/N`, `2/N`, у каждой тот же тег и ключ доставки с partNumber. Нельзя скрывать риски или часть матчей ради лимита. Это одно логическое сообщение дедлайна, состоящее из нескольких Telegram сообщений; увеличение нагрузки учитывается. REVIEW: если строго требуется один Telegram message при любом размере, нужен отдельный выбор формата файла/изображения.

## Время и ошибки {#errors}

08:00 импорт, 08:10 запуск общего обновления, 09:00 старт рассылки по дате дедлайна в `Europe/Moscow`. Зависимости и cutoff задаёт `spec://modules/telegram/INFRA-005-deadline-pipeline#pipeline`. При неполных данных отправляется честный отчёт с предупреждением, а не выдуманное заключение. Если дедлайн раньше 09:00, обычный сценарий физически опаздывает: draft предлагает предыдущий день 08:00/08:10/09:00, с пометкой «дедлайн завтра». До принятия этой политики такой тур исключается из обычной утренней кампании с операторским сигналом.

Блокировка бота пользователем прекращает попытки. Нет Sports профиля/команды/подписки — нет персонального анализа; настройки объясняют недостающее. Повторный webhook/рестарт не создаёт второй отчёт. Перенос дедлайна не означает автоматического второго уведомления без отдельной correction policy.

## API {#contracts}

Предлагаемые endpoints: `POST /api/profile/telegram/link-session`, `POST /api/profile/telegram/link-code`, `POST /api/profile/telegram/confirm`, `GET /api/profile/telegram`, `DELETE /api/profile/telegram`, `PUT /api/profile/telegram/subscriptions`, `POST /api/telegram/webhook`. Не реализованы в текущем проходе. Все profile endpoints используют текущую session auth; webhook использует отдельный Telegram secret и durable inbox.

## Трассировка {#traceability}

Будущие точки `@spec` — профильный UI, link service, webhook, renderer, signal classifier и прямые contract tests. Planned namespace `src/server/telegram/`; до активации draft production-код не размечается.

## Критерии готовности {#acceptance}

- Привязка проходит через кнопку и ручной код; проверены границы 15 секунд, grace, повтор, две вкладки, гонка двух Telegram ID, expiry, CSRF, конфликт действующих связей и pause/unlink.
- Доставка не начинается без consent; секреты не попадают в логи/кэш; цифры Telegram ID не теряются.
- Различаются опубликованный Sports состав и последние замены; сохранённые планы не затираются импортом.
- ALT 0/null/округление, blank/unknown, капитан/скамейка, другой кубок, двойной тур и неполный маппинг имеют проверенные результаты.
- На каждом дедлайне свой тег и три столбца; проверены лимит 4096, HTML escaping и мобильный вид.
- Одновременные турниры, ранний дедлайн, перенос, неактивный аккаунт и отписка во время очереди покрыты проверками.
