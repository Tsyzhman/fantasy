<a name="root"></a>

# Персональный доступ агентов к Fantasy Scout {#root}

Владелец аккаунта подключает агентский клиент к Fantasy Scout и выбирает, какие действия разрешить конкретному клиенту. За учётную запись и вход через браузер отвечает `spec://common/FEAT-009-session-authentication#root`, за операции с составами и процессами — `spec://modules/agents/FEAT-017-squad-workflows#root`.

<a name="keys"></a>

## Ключ в профиле {#keys}

Пользователь в своей веб-сессии создаёт именованный ключ с выбранными разрешениями и сроком действия. Интерфейс показывает секрет при создании. Для последующего использования профиль показывает название, разрешения, срок, статус и время последнего использования. Пользователь отзывает выбранный ключ. Отзыв одного ключа сохраняет возможность пользоваться другими действующими ключами аккаунта.

Сервис генерирует криптографически случайный секрет, хранит его хеш и определяет пользователя по проверенному ключу. Журнал связывает обращение с ключом, действием, временем и исходом. Секреты, заголовки авторизации и полные аргументы в журнал не попадают.

<a name="authorization"></a>

## Разрешения {#authorization}

Каждый запрос требует действующий ключ и активный аккаунт. Выполнение операции ограничено разрешениями ключа, действующими правами пользователя и принадлежностью объекта. Каталог показывает инструменты, доступные с данным ключом. Динамические права конкретных шагов процесса проверяются при выполнении. Идентификаторы ключей, процессов, составов и запусков другого пользователя не дают доступа к его данным.

Каталог разрешений включает `squads:read`, `squads:write`, `workflows:read`, `workflows:write`, `workflows:test`, `workflows:publish` и `workflows:run`. Тест и публикация имеют собственные разрешения. Рабочая запись в состав всегда требует `squads:write`.

<a name="transport"></a>

## Вызов клиента {#transport}

Удалённый MCP по Streamable HTTP доступен на `/api/mcp`. Профиль документирует подключение с персональным Bearer. Версионированный HTTP API и MCP публикуют один каталог с именами, описаниями, схемами аргументов и результатами одних и тех же команд. Вход через браузер сохраняет существующее поведение. Запрос через любой агентский транспорт проходит проверку аргументов и полномочий. Закрытые ответы не кэшируются общим кэшем.

Из корневого README и инструкций агента доступен порядок подключения. Для знакомства с репозиторием ключ не требуется. При первом обращении к личным данным агент просит владельца скопировать из профиля полный адрес MCP и настроить персональный ключ в хранилище секретов клиента. Агент называет права для конкретной задачи. Первое обращение получает каталог доступных инструментов.

Агент, которому известен только адрес сайта, может до входа перейти со страницы авторизации к публичной инструкции `/llms.txt`. Она описывает способ получить адрес и ключ у владельца и проверить доступ первым вызовом. Личные данные и сами инструменты по-прежнему доступны только с действующим ключом.

<a name="acceptance"></a>

## Приёмка {#acceptance}

Реальный MCP-клиент получает список инструментов и вызывает доступный инструмент. Пользователь с ключом для чтения получает отказ при записи. После отзыва, истечения срока или отключения аккаунта следующий запрос отклоняется. Два пользователя независимо управляют своими ключами. Проверки транспорта проходят также через версионированный HTTP API.
