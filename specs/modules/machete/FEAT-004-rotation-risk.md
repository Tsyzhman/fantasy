# FEAT-004: RR — риск ротации {#root}

## Простыми словами {#plain-language}
Игрок получает показатель риска не попасть в старт по наблюдаемой истории стартов/скамейки и отдыху. Это начальная эвристика, не откалиброванная вероятность.

## Цель и границы {#scope}
Показать RR в планировщике и применить в «Надёжной». Прогноз EP, режимы balanced/upside/GLOBAL_AUTO и K не меняются. Нагрузка и тренд отдельно не добавляются; подбор весов и риск травм вне scope.

## Цель {#goal}
Сделать риск ротации отдельным объяснимым показателем по утверждённой пользователем формуле, с явной доступностью исходных данных.

## Участники {#actors}
Пользователь планировщика видит RR и выбирает режим подбора. Существующий ingestion заполняет нормализованную историю, а фоновый materializer обновляет пул без запросов истории на каждый рендер.

## Управляющие спеки {#governing-specs}
Самостоятельный контракт риска игрока; Constraint: `spec://modules/machete/FEAT-001-global-ranking-strategy#contracts`.

## Данные {#data}
Источник — MatchPlayerStat.started/minutes и CoreMatch.finished/cancelled/matchDate по внутреннему playerId. Расписание ближайшего матча берётся из того же пула/турнира. Добавляется компактное поле rotationRisk в player DTO и metadata версии/истечения RR в существующем JSON снимка. Новых таблиц и миграций нет.

## Формула {#formula}
Для N = 50,20,10,5 взять последние не более N завершённых наблюдений с известным started. RN = BenchN / (StartsN + BenchN). started=false означает известную скамейку, включая выход на замену; started=null и отсутствие записи не означают скамейку. Дубликаты matchId учитываются один раз. Неполные окна используют фактическое число наблюдений с отметкой малой выборки, без выдумывания недостающих игр.

restDays — полные интервалы 24 часа между последним завершённым матчем игрока с minutes>0 и ближайшим будущим kickoff. Шкала 0–1/2/3/4/5+ дней: 1/0.72/0.40/0.16/0 (исходные 0.25/0.18/0.10/0.04/0 делятся на 0.25).

RR = clamp(0.15 R50 + 0.20 R20 + 0.25 R10 + 0.25 R5 + 0.15 Rrest, 0, 1).

При нулевой истории, неизвестном отдыхе или kickoff итог null с причиной. Никаких данных из будущего: завершённые матчи должны быть раньше min(observedAt, kickoff). Результат содержит версию RR_V1, kickoff, observedAt, четыре компактных окна и причины; полная история в клиент не передаётся.

## Контракты {#contracts}
Чистое ядро `src/machete/rotation-risk.ts`; загрузка `src/server/rotation-risk.ts`. Для одного пула IDs дедуплицируются; один SQL-запрос на пакет до 250 игроков, до 50 строк истории на игрока и последнее появление, без запросов HTTP и постоянного дополнительного кэша. История ограничена существующими нормализованными наблюдениями FotMob во всех загруженных соревнованиях; показатель не утверждает полноту отсутствующих составов.

Пул/DTO/Worker передают `rotationRisk`. В «Надёжной» при пригодном RR score = max(0, consensusEP × (1−RR) × (0.75+0.25 confidence) × sourceMultiplier). confidence имеет существующий fallback 0.55, sourceMultiplier сохраняется. Прежние штрафы минут/appearance/числа risk notes повторно не добавляются. При неизвестном или устаревшем RR сохраняется прежний reliable score. RR для ближайшего матча применяется как текущий критерий надёжности состава, не как вероятность всех матчей горизонта.

RR имеет TTL 24 часа и истекает не позже kickoff. Снимки с RR_V1 обновляются последовательно при отсутствии версии или истечении TTL; старый пул остаётся читаемым. Изменение исходной истории отражается при очередном обновлении пула.

## Сценарии и ошибки {#scenarios}
Колонка «RR %» доступна по умолчанию новым настройкам таблицы и в выборе колонок существующим. Tooltip объясняет окна/отдых/нехватку данных. Неизвестный/устаревший RR показывается как «—», без подмены на 0%. До обогащения лёгкого пула RR неизвестен.

## Ошибки {#errors}
NO_KNOWN_LINEUPS, UNKNOWN_REST и NO_FUTURE_FIXTURE дают итог null. SHORT_HISTORY допускает расчёт на фактических окнах и показывается как ограничение выборки. Истёкшая/чужая версия или некорректное числовое значение RR не используется. Ошибки БД остаются ошибками существующего обновления пула; прошлый READY снимок сохраняется штатным механизмом.

## Приёмка {#acceptance}
Пример R50=.2,R20=.25,R10=.3,R5=.4,rest=2 даёт .363. Все пороги отдыха, границы 0/1, пустая/короткая история, дубликаты, неизвестные статусы и будущие данные покрыты тестами. Проверены DTO, reliable fallback/сохранение EP, пакетирование и column preferences. Production build и относящиеся к изменению проверки проходят. Live DB smoke выполняется при доступном окружении; не заменяется утверждением о полноте данных.
