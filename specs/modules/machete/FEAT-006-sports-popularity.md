# FEAT-006: Популярные игроки Sports перед туром {#root}

## Простыми словами {#plain-language}

Собираем опубликованные Sports списки покупок, продаж, популярных игроков и капитанов. Цель — до 15 игроков в каждой доступной категории; 10 или меньше допустимы. Если данных нет, честно показываем отсутствие данных. Процент владения игроком не выдаём за число покупок.

## Цель {#goal}

Сделать опубликованные рейтинги доступными в контексте выбранного тура с проверяемым источником и временем. Источники и фактическая проверка: [исследование](../../work/evidence/WI-030/research.md#sports).

## Управляющие документы {#governing-specs}

Legacy product canon: `specs/common/main.md`. Это проект новой возможности, реализация отдельно. Потребитель: `spec://modules/telegram/FEAT-007-deadline-assistant#message`.

## Участники и запуск {#actors}

Общий worker собирает публичные источники по расписанию и по запросу pipeline; пользователь читает готовый рейтинг выбранного тура на сайте или в боте. Оператор разбирает ошибку mapping/источника без ручного заполнения выдуманных значений.

## Границы {#scope}

Входит: публичный HTTP/GraphQL Sports, нормализация, привязка к сезону/турниру/туру, общий снимок трендов, чтение сайтом и ботом. Не входит: обход закрытого состава, сбор всех команд пользователей для вычисления рынка, замена FantasyPlayerPrice, автоматические покупки игроков или пересчёт моделей прогнозов.

## Источники и семантика {#sources}

1. Лента `https://www.sports.ru/fantasy-sports/news/` и связанные статьи Sports с явным турниром, сезоном и туром. Разбор основного HTML статьи, без комментариев, рекомендаций и рекламы. JSON-LD используется для canonical URL и даты; `articleBody` может содержать только анонс — это подтверждено проверкой.
2. Уже используемый `https://www.sports.ru/gql/graphql/`, `fantasyQueries.players.list.status.selectedBy`: доля выбора, в проекте `FantasyPlayerPrice.selectedByPercent`. Это источник категории `OWNERSHIP`, а не подтверждённых покупок. Не добавлять запрос на каждого подписчика.
3. История сравнимых снимков ownership может дать `OWNERSHIP_DELTA_PP`. Рост 20% → 23% означает +3 процентных пункта, а не 3 покупки и не доказанный чистый трансферный поток. Состав участников мог измениться.

Категории: `BUYS`, `SELLS`, `OWNERSHIP`, `CAPTAINS`, `OWNERSHIP_DELTA_PP`. Статья может называть список покупками и приводить изменение популярности: сохранять исходную категорию и отдельно `metricKind=reported_popularity_change`, единицу и формулировку источника; не превращать проценты в количество. Фильтр «топ-1000 менеджеров» хранить как `populationScope`, не смешивать со всеми менеджерами. Поздняя публикация не гарантированно существует к 09:00.

## Сценарии {#scenarios}

- Один общий collector проверяет ленту каждые 30 минут, только для поддерживаемых текущих соревнований; дедлайн-процесс также запрашивает обновление в 08:10 МСК. Совпавшие запуски объединяются одним lease.
- Новая релевантная статья разбирается один раз; изменившаяся статья получает новую ревизию по hash содержимого. Сбор прекращается после дедлайна для его утреннего отчёта; поздние публикации могут сохраняться как история.
- Из каждого опубликованного рейтинга берём первые `min(15, available)` уникальных игроков в исходном порядке. Списки по позициям не называются общим топом. Для OWNERSHIP из API общий топ-15 строится только после полной пагинации всего пула, а не из 15 самых дорогих игроков.
- Сайт/бот показывают категорию, значение и единицу, количество найденных игроков, время публикации/среза, ссылку Sports и ограничения выборки. Предлагаемое место на сайте — блок «Популярное на Sports» в контексте выбранного тура Squad; существующие таблицы и действия сохраняются.
- Нет статьи нужного тура → `NOT_PUBLISHED`. Можно отдельно показать свежий OWNERSHIP с корректной подписью. Статья прошлого тура не подставляется молча.

## Данные и идентичность {#data}

Предлагаемые новые таблицы, без копирования каталога игроков:

| Сущность | Основные поля и ограничения |
|---|---|
| `SportsTrendSource` | canonicalUrl UNIQUE, sourcePublishedAt, fetchedAt, contentHash, parserVersion, parseStatus; URL только разрешённого Sports host |
| `SportsTrendSnapshot` | contestId, season, providerRoundId, category, metricKind, unit, populationScope, sourceId, revision, status, observedAt; UNIQUE(sourceId, revision, category, populationScope) |
| `SportsTrendEntry` | snapshotId, sourceRank, providerPlayerId nullable, playerId nullable, sourceName, sourceTeam, sourcePosition, value nullable; UNIQUE(snapshotId, sourceRank) |

Ранжирование, dedup и mapping выполняются до публикации снимка. Существующие provider IDs/маппинг приоритетны. Для статьи без ID допустимо строгое уникальное совпадение имени, клуба/сборной и позиции в данном сезоне; неоднозначность остаётся `UNMAPPED`, имя источника сохраняется. Повтор одного игрока внутри одной категории отклоняется либо объединяется с evidence; не удалять одноимённого другого игрока. Национальные команды и клубы не взаимозаменяемы.

Тур определяется по метаданным и тексту статьи, не только по дате публикации. Если связь с туром недоказуема, запись не используется как тренд этого дедлайна. Снимки без round допустимы только для явно помеченного текущего ownership.

## Контракты {#contracts}

Предлагаемый read API: `GET /api/machete/sports-trends?contestId=...&providerRoundId=...`. Использует существующую session auth, возвращает `status`, категории, источник, timestamps, `availableCount`, до 15 entries каждой категории. Нет данных — нормальный ответ `NOT_PUBLISHED`, а ошибка парсера отдельно `FAILED`. Персональных данных в общем снимке нет. Бот читает тот же материализованный результат.

Parser/collector не вызывает AI на каждый материал или пользователя. Ограничения начального запуска: concurrency=1, до 3 страниц ленты и 20 новых/изменённых статей за цикл, таймаут HTTP 20 секунд, тело до 2 MiB, максимум 3 попытки с backoff/jitter. `429` учитывает Retry-After; защитная страница/403 не обходится и не распознаётся как пустой рейтинг.

## Ошибки, кэш и хранение {#errors}

Невалидные единицы, конфликт турнира/тура, повторные ranks, невозможные проценты или неполная загрузка запрещают публикацию новой версии. Сохраняется прежняя версия того же тура с явной отметкой времени/ошибки. Отсутствующее значение остаётся `null`, а не 0. В существующем `sportsRuSelectedByPercent` есть `Number(value)`: новый контракт требует проверить `null` до преобразования, иначе `Number(null)` создаст ложный ноль.

HTTP conditional requests при поддержке сервера; кэш ленты 30 минут. Хранить нормализованные рейтинги 90 дней, ограниченное parser evidence максимум 7 дней и 100 MiB суммарно. Полные статьи постоянно не архивировать. История ownership: один общий снимок на contest/временной bucket, максимум 30 дней; удаление батчами. Логи не содержат пользовательских профилей и HTML.

## Трассировка {#traceability}

Будущие точки `@spec`: каталог `src/providers/sports-ru-trends/`, новый trends service в `src/machete/`, collector, read API и прямые parser/contract tests. Существующий ценовой импорт остаётся владельцем текущего selectedBy; новый модуль владеет рейтингами и историей, не дублирует импорт цен. Эти новые компоненты пока не реализованы.

## Критерии готовности {#acceptance}

- Реальный HTML пример распознаёт 10 покупок и 10 продаж; тест JSON-LD с коротким анонсом не теряет HTML-списки.
- Проверены списки из 0/3/10/15/более 15 игроков, позиции, капитаны, выборка топ-1000, запятые в процентах, повторная публикация и неоднозначное имя.
- OWNERSHIP, покупки и изменение ownership различаются в данных и UI; `null` не становится 0.
- Точный тур/сезон, полная API-пагинация, source URL и freshness проверяются до показа; поздняя публикация не считается доступной к 09:00 задним числом.
- Повтор цикла не создаёт дубли; есть bounded retention, размер кэша и метрики skipped/failed/unmapped.
