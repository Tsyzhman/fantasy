# Сбор и разбор данных FotMob

Эта памятка предназначена для AI-агента. Она намеренно не привязана к названиям файлов, функций, классов или экранов проекта. Здесь описаны фактический способ получения данных, логика разбора JSON и рекомендуемая схема надежного сбора.

## Коротко

Используется именно API: неофициальные внутренние JSON-endpoint'ы сайта FotMob. Это не HTML-парсинг страниц и не браузерная автоматизация. Данные забираются обычными HTTP GET-запросами.

При этом это не официальный лицензированный API с выданным ключом, опубликованным контрактом и гарантией стабильности. Используются те же внутренние endpoint'ы, к которым обращается веб-сайт FotMob. Поэтому метод технически является работой с API, но этот API может изменить URL или структуру ответа без предупреждения.

Полные данные матча получаются через внутренний Next.js endpoint:

```text
https://www.fotmob.com/_next/data/{buildId}/match/{matchId}/playbyplay.json
```

`buildId` извлекается из HTML главной страницы FotMob. Этот endpoint возвращает точный матч по `matchId` и не требует подписи `x-mas`, cookie или прохождения Cloudflare Turnstile.

Главный принцип сбора:

```text
лига и сезон
→ состав участников и ростеры
→ список матчей
→ краткая карточка каждого матча
→ полный JSON каждого матча
→ проверка ответа
→ нормализация
→ идемпотентная запись
```

### Какие API используются

В основном потоке два типа API-запросов:

1. Внутреннее web API под префиксом `https://www.fotmob.com/api/data/`. Через него получаются лига, команды, составы, календарь и краткая карточка матча.
2. Внутренний Next.js data API под префиксом `https://www.fotmob.com/_next/data/`. Через него получается полный JSON конкретного матча со статистикой игроков, команд, ударами, событиями и lineup.

HTML используется только как служебный шаг: из главной страницы извлекается текущий `buildId`, необходимый для URL Next.js data API. Сами футбольные данные из HTML не извлекаются.

Практическая классификация:

| Вопрос | Ответ |
| --- | --- |
| Используется ли API? | Да |
| Это официальный публичный API FotMob? | Нет |
| Нужен ли API key для основного сбора? | Нет |
| Нужен ли headless-браузер? | Нет |
| Парсятся ли футбольные данные из HTML? | Нет |
| Что парсится? | JSON-ответы внутреннего API |
| Есть ли гарантия стабильности схемы? | Нет |

## Как именно получаем данные

### 1. Метаданные лиги, команды и список матчей

Используются запросы:

```http
GET https://www.fotmob.com/api/data/leagues?id={leagueId}&season={season}&ccode3=GBR
GET https://www.fotmob.com/api/data/teams?id={teamId}&ccode3=GBR
GET https://www.fotmob.com/api/data/fixtures?id={leagueId}&season={season}&ccode3=GBR&timezone=Europe/London
```

Для определения текущего сезона metadata sync сначала вызывает league endpoint
без сохранённого `season`. Только после обновления сезона выполняются команды и
матчи. Это предотвращает фиксацию на прошлом сезоне после летнего rollover.

При получении матчей сначала используется массив:

```text
fixtures.allMatches
```

из ответа лиги. Он предпочтительнее отдельного запроса списка матчей, потому что обычно содержит номер тура. Отдельный endpoint списка матчей — запасной вариант, если в ответе лиги подходящего массива нет.

Команды сначала берутся из турнирной таблицы:

```text
table[].data.table.all[]
```

Если таблицы нет, команды извлекаются из домашних и гостевых участников матчей. Значения-заглушки вроде `TBD`, `Winner A`, `W12` отбрасываются. После этого для каждого числового `teamId` отдельно загружается карточка команды и ее состав.

Сезон приводится к полному виду: например, `2025/26` превращается в `2025/2026`. Для турниров, обозначаемых одним годом, используется этот год без искусственного диапазона.

### 2. Краткая карточка матча

Перед полным ответом запрашивается:

```http
GET https://www.fotmob.com/api/data/match?id={matchId}
```

Из нее получаются базовые сведения о матче: участники, дата, счет и статус. Пустой ответ или карточка без валидных идентификаторов считаются ошибкой, а не успешным импортом.

### 3. Полный JSON матча

Сначала один раз за процесс загружается главная страница:

```http
GET https://www.fotmob.com/
```

Из HTML регулярным выражением извлекается:

```regex
"buildId":"([^"]+)"
```

Затем выполняется:

```http
GET https://www.fotmob.com/_next/data/{buildId}/match/{matchId}/playbyplay.json
```

Из ответа берется объект `pageProps`. В нем ожидаются:

```text
general
header
content.matchFacts
content.playerStats
content.shotmap
content.stats
content.lineup
```

Достаточно наличия хотя бы одного подробного раздела, чтобы ответ считался детальным на транспортном уровне. Для качественного production-сбора этого условия недостаточно — ниже описана более строгая проверка.

`buildId` кэшируется в памяти. Если запрос полного JSON вернул `404`, `buildId` сбрасывается, повторно извлекается из главной страницы, после чего запрос матча повторяется один раз с новым значением.

### Почему не используется URL через slug

Не следует получать полный JSON через редирект от условного `/match/{id}.json` к `/matches/{slug}`. Slug может быть общим для нескольких матчей одной пары команд. В таком случае FotMob способен вернуть другой матч той же пары.

Endpoint `playbyplay.json` использует `matchId` непосредственно в URL, поэтому после получения ответа остается только проверить совпадение идентификатора.

### Подпись и cookie

Основной сбор не использует `x-mas` и cookie.

Подписанный endpoint данных отдельного игрока является вторичным путем. Он может требовать и `x-mas`, и актуальную cookie с пройденным Turnstile. Для основного импорта игроки собираются из составов команд, lineup, статистики, ударов и событий матча, поэтому этот endpoint не нужен.

Если режим источника явно не переключен на неофициальные HTTP-endpoint'ы, проект использует локальные тестовые данные. Для реального сбора это переключение обязательно.

## Транспортная защита

Запросы отправляются с обычными браузероподобными заголовками:

```text
User-Agent
Accept
Accept-Language
Referer
```

Текущая безопасная схема:

- таймаут одного запроса — 20 секунд;
- минимальный интервал между запросами — 1500 мс;
- запросы выполняются последовательно;
- для обычных JSON-запросов — до 5 попыток;
- для Next.js JSON — до 3 попыток;
- повторные попытки используют экспоненциальную задержку от 750 мс и случайный jitter до 500 мс;
- для `403`/`429`, если это не Turnstile, используется более длинная базовая задержка — 3 секунды;
- Turnstile-ошибка не повторяется бесконечно: она считается постоянной для текущей сессии.

Это медленно, но безопаснее агрессивного параллельного обхода. Ограничение скорости нельзя отключать при массовом сборе.

## Проверка полного ответа

До парсинга обязательно проверяется:

1. Ответ является JSON.
2. В ответе есть непустой `pageProps`.
3. Идентификатор из `general.matchId`, `header.matchId`, корневого `matchId` или `id` строго равен запрошенному `matchId`.
4. В `content` есть хотя бы один подробный раздел: `playerStats`, `shotmap`, `lineup`, `stats` или `matchFacts`.

Несовпадение идентификатора нельзя исправлять подстановкой запрошенного ID. Такой ответ нужно отклонить, иначе статистика одного матча окажется записана в другой.

## Как разбирается JSON

### Общий контекст матча

Базовые поля читаются с несколькими запасными путями, потому что форма ответа менялась:

- идентификатор матча — из корня, `general` или `header`;
- лига и сезон — из обертки, корня, `general` или `header`;
- хозяева и гости — из `general`, `header`, корневых `home`/`away` или массива команд;
- статус — из `status`, `header.status` или `general.status`;
- время — прежде всего UTC-поля, затем остальные даты;
- счет — из карточек команд или корневых полей;
- тур — из `round`, `roundName` и аналогичных полей.

Идентификаторы лиги, команды, игрока и матча считаются авторитетными идентификаторами источника и хранятся как целые числа. Имя не используется как основной ключ.

### Команды и игроки

Для матча создаются две команды — хозяева и гости. Игроки объединяются по числовому `playerId` из нескольких источников:

- статистика игроков;
- стартовый состав и запасные;
- удары;
- голы, карточки, замены и другие события;
- вложенные объекты игроков внутри полного JSON.

Если имя найдено в одном разделе, а участие и команда — в другом, сведения объединяются по `playerId`.

### Статистика игроков

Сначала проверяются точные пути:

```text
playerStats
content.playerStats
content.lineup.playerStats
content.lineup.lineup
content.lineups
lineups
```

Массивы рекурсивно разворачиваются через контейнеры:

```text
players
members
lineup
starters
substitutes
subs
```

При разворачивании вниз передается контекст команды. Для `starters` дополнительно выставляется признак выхода в старте. Если статистика не содержит команду, она дополняется из lineup по `playerId`.

Числа читаются в два прохода:

1. прямые поля и известные варианты их имен;
2. рекурсивный поиск внутри `stats`, `groups`, `items`, `children`, `sections` по нормализованной подписи показателя.

Подпись приводится к нижнему регистру, из нее удаляются скобки, пробелы и знаки препинания. Вложенное значение извлекается из `value`, `displayValue`, `total` или `stat.value`.

Нормализуются как минимум:

- минуты, позиция, номер, старт и замены;
- голы, передачи, карточки, сейвы, пропущенные голы и сухой матч;
- `xG`, `xGOT`, `xA`;
- удары и удары в створ;
- созданные моменты и ключевые передачи;
- отборы, перехваты, выносы, выигранные единоборства и верховые дуэли;
- возвраты владения, касания в штрафной, заработанные фолы и пенальти;
- рейтинг.

Отсутствующее значение остается `null`. Его нельзя автоматически превращать в `0`: источник часто просто не присылает показатель.

### Командная статистика

Основной источник:

```text
content.stats.Periods.All.stats
```

Структура обходится рекурсивно через `stats`, `groups`, `items`, `children`, `sections`. Из каждой строки берутся подпись показателя и пара значений хозяев/гостей.

Поддерживаются числа, десятичные дроби с точкой или запятой и проценты. Значения вроде `421 / 487` не выдаются за одно число.

Разбираются:

- счет;
- `xG`, `xGOT`, `xA`;
- удары, створ, мимо, блоки;
- большие моменты и упущенные большие моменты;
- касания в штрафной;
- владение, передачи, точные передачи и точность;
- угловые, офсайды, фолы, карточки;
- отборы, перехваты, выносы и сейвы.

Если агрегат удара отсутствует в командной статистике, он восстанавливается по `content.shotmap.shots`: считаются удары, голы, створ, блоки, сумма `xG` и сумма `xGOT`. Если командный `xA` отсутствует, используется сумма найденных индивидуальных `xA`.

На один матч ожидаются две строки командной статистики: одна для хозяев, одна для гостей.

### Удары

Основной путь:

```text
content.shotmap.shots
```

Сначала проверяются известные точные пути. Если они не найдены, выполняется ограниченный поиск вложенного массива, похожего на массив ударов. Массив признается подходящим по наличию координат, `expectedGoals`, `playerId` или `teamId`.

Для каждого удара извлекаются:

- матч, команда, соперник и игрок;
- минута и добавленное время;
- исходные `x` и `y`;
- тип события, тип удара, часть тела и ситуация;
- гол, створ, блок и большой момент;
- `xG` и `xGOT`.

Координаты FotMob на поле `105 × 68` переводятся в проценты `0–100`. Если явно указано направление атаки справа налево, продольная координата отражается. Если направление не указано, координаты только масштабируются — выдумывать направление нельзя.

Для защиты от дублей строится стабильный fingerprint из матча, команды, игрока, минуты, добавленного времени, координат, типа события и исходного ID события.

### События

События ищутся по путям:

```text
content.matchFacts.events.events
content.matchFacts.events
content.events.events
content.events
events
incidents
```

Извлекаются команда, основной и связанный игрок, минута, добавленное время, тип и подтип. Отдельно нормализуются признаки гола, голевой передачи, автогола, пенальти, карточки и замены.

Объекты с координатами удара не считаются обычными событиями, даже если лежат рядом в JSON.

### Восстановление связей

После первичного разбора выполняется второй проход:

- команда восстанавливается по признаку хозяева/гости;
- соперник определяется как другая команда матча;
- отсутствующая команда игрока восстанавливается по однозначной связи этого игрока со статистикой, ударом или событием;
- команда события восстанавливается по основному или связанному игроку;
- автогол не используется как доказательство обычной принадлежности игрока к команде;
- строки статистики без положительного идентификатора команды или игрока отбрасываются;
- число восстановленных и отброшенных связей учитывается как метрика качества.

## Как данные записываются сейчас

Нормализованный результат записывается транзакционно и идемпотентно:

- матч — по `matchId`;
- командная статистика — по паре `matchId + teamId`;
- статистика игрока — по паре `matchId + playerId`;
- удар — по `matchId + fingerprint`;
- события перед новой записью полностью заменяются для матча;
- отсутствующие справочные сущности временно создаются как placeholders, чтобы не ломать внешние ключи;
- после появления настоящих данных placeholders обновляются;
- после изменения ударов сбрасывается связанный кэш карт ударов.

Для незавершенного матча полный JSON сохраняется вместе с хешем, версией парсера и версией схемы. Для завершенного матча с подробным payload сырой JSON сейчас удаляется после успешной нормализации.

Завершенный матч при следующем обычном запуске пропускается, если в базе уже есть хотя бы одна нормализованная строка командной статистики, статистики игрока или удара. Для повторного получения нужен принудительный refresh, а для повторного разбора — сохраненный raw payload.

После статистики игроков могут отдельно рассчитываться производные fantasy-показатели. Это уже не часть парсинга FotMob.

## Как собирать лучше

### 1. Разделить обнаружение и загрузку деталей

Не делать один длинный запрос «собрать лигу». Сначала сохранить список матчей и их статусы, затем создать отдельную задачу на каждый `matchId`. Это дает независимые повторы, понятный прогресс и возобновление после сбоя.

### 2. Хранить raw отдельно от нормализованных данных

Лучший вариант:

```text
raw JSON + hash + fetched_at + parser_version + schema_version
→ проверка
→ нормализованные таблицы
```

Сырой JSON завершенных матчей лучше хранить сжатым в дешевом объектном хранилище, а не удалять полностью. Иначе после исправления парсера историю придется повторно скачивать, а если endpoint изменится, старые данные восстановить будет невозможно.

Минимально допустимый компромисс — хранить последний raw, его хеш и ссылку на архив. Если новый хеш совпадает со старым, повторный разбор не нужен.

### 3. Ввести явный признак полноты

Проверка «есть хотя бы одна нормализованная строка» слишком слабая. Для завершенного матча нужно сохранять отдельные признаки:

```text
metadata_ok
team_stats_ok
player_stats_ok
shots_ok
events_ok
payload_validated
normalized_at
```

Матч можно объявлять полностью собранным только по контракту конкретного продукта. Например, для fantasy обязательна статистика игроков, а для карты ударов — массив ударов или явное доказательство, что ударов было ноль.

### 4. Не путать пустое значение и отсутствие раздела

`shots: []` может означать реальный матч без ударов, а отсутствие `shotmap` — неполный ответ. Аналогично `0` и `null` имеют разный смысл. В raw-слое нужно сохранять информацию о наличии самого раздела.

### 5. Обновлять по статусу матча

Рекомендуемый режим:

- ростеры и календарь — 1–4 раза в сутки;
- матчи до начала — обновлять только для времени, тура и переносов;
- live — каждые 1–2 минуты с ограничением общей нагрузки;
- только что завершенные — повторить через 10 минут, 1 час и 24 часа, потому что источник может исправить статистику;
- старые завершенные и полностью проверенные — не запрашивать без причины;
- после изменения версии парсера — разбирать сохраненный raw, а не скачивать весь архив заново.

### 6. Ограничить параллелизм

Безопасный старт — один запрос за раз с интервалом не меньше 1.5 секунды. Если нужна скорость, лучше несколько независимых очередей с общим лимитером, но не бесконтрольный `Promise.all` по сотням матчей.

Рекомендуется не больше 1–2 одновременных запросов к одному host до получения реальных метрик по `429`, таймаутам и времени ответа.

### 7. Делать обновление набора ударов атомарным

Текущая запись ударов только добавляет или обновляет строки по fingerprint. Если источник удалил или исправил старый удар так, что fingerprint изменился, прежняя строка может остаться.

Надежнее в одной транзакции заменить весь набор ударов матча после успешного разбора нового полного payload либо помечать ревизию payload и удалять строки старой ревизии.

### 8. Не скрывать частичные сбои

Ошибка одного матча может не останавливать массовую загрузку, но итоговая задача не должна выглядеть полностью успешной. Нужны как минимум:

- число найденных, скачанных, пропущенных и упавших матчей;
- последний обработанный `matchId` для каждого сезона;
- причина последней ошибки;
- число восстановленных и отброшенных связей;
- контроль возраста raw, который еще не был нормализован;
- отдельный статус `completed_with_errors`.

Для строгого backfill лучше падать на неполном детальном payload. Для ежедневного обновления допустимо продолжить остальные матчи и поставить неудачный матч в очередь повторов.

### 9. Защититься от расширения scope

До массового обхода нужно проверить:

- все найденные матчи относятся к запрошенной лиге;
- сезон совпадает;
- число матчей не превышает разумный лимит;
- диапазон дат не выглядит как несколько случайно склеенных сезонов;
- временные команды-заглушки не попали в справочник;
- известные алиасы турниров приведены к одному каноническому ID.

### 10. Следить за изменением схемы

Публичные endpoint'ы не являются стабильным лицензированным API и могут измениться без предупреждения. Поэтому нужны:

- сохраненные обезличенные fixtures JSON для тестов парсера;
- счетчики найденных разделов и строк каждого типа;
- тревога, если вчера статистика игроков была у большинства завершенных матчей, а сегодня исчезла у всех;
- лог неизвестных названий статистик;
- smoke-проверка на нескольких известных завершенных матчах после каждого изменения клиента или парсера.

## Рекомендуемый алгоритм

```text
для каждого разрешенного сезона лиги:
    получить метаданные лиги
    определить фактическое обозначение сезона у источника

    получить список команд
    для каждой команды последовательно получить состав
    upsert команд, игроков и сезонных ростеров

    получить fixtures.allMatches
    если массива нет — получить отдельный fixtures endpoint
    отфильтровать статусы и проверить границы scope

    для каждого matchId:
        сохранить или обновить краткую карточку матча

        если матч завершен и есть строгий completeness marker:
            пропустить

        получить краткий JSON матча
        получить актуальный buildId
        получить playbyplay.json

        если 404:
            один раз обновить buildId и повторить

        проверить matchId и наличие требуемых разделов
        посчитать hash raw JSON

        разобрать metadata, teams, players
        разобрать team stats, player stats, shots, events
        восстановить только однозначные связи
        выполнить проверки качества

        в одной транзакции:
            сохранить raw или ссылку на raw
            upsert нормализованные сущности
            атомарно заменить изменяемые наборы матча
            сохранить completeness markers и версию парсера

        обновить checkpoint и счетчики
```

## Минимальный набор проверок качества

Для завершенного матча агент должен проверить:

- запрошенный и полученный `matchId` совпали;
- хозяева и гости имеют разные положительные ID;
- статус, время и счет согласованы с краткой карточкой;
- у каждой строки указан правильный `matchId`;
- нет дублей игроков по `matchId + playerId`;
- есть ровно две командные строки либо записана явная причина их отсутствия;
- сумма ударов по shotmap не противоречит командным totals без зафиксированного объяснения;
- `xG` ударов и командный `xG` сравниваются с допустимой погрешностью, а не на строгое равенство float;
- неизвестные поля не приводят к падению всего payload, но фиксируются как schema drift;
- нули не подставляются вместо отсутствующих данных;
- частичный payload не помечается полным.

## Фактические слабые места текущего подхода

Без смягчения:

1. Используется неофициальный и недокументированный путь FotMob. Он может сломаться в любой момент.
2. Сырой JSON завершенных матчей удаляется, поэтому исправление парсера требует повторного скачивания истории.
3. Проверка уже нормализованного завершенного матча считает достаточной любую одну строку статистики или удара. Частично разобранный матч может больше не обновиться автоматически.
4. Удары не заменяются целиком. После исправления данных источником возможны устаревшие строки.
5. Ошибка синхронизации ростера записывается, но сама обработка сезона продолжается. В результате матчи могут быть загружены при неполном ростере.
6. Последовательный сбор надежен, но полный backfill большого числа лиг занимает долгое время.
7. Наличие одного подробного раздела подтверждает форму payload, но не его полноту для конкретного продукта.

Это не причины отказываться от текущего метода. Это места, которые другой агент должен учитывать и не выдавать за уже решенные.
