# Sports trends и Telegram перед дедлайном

Дата исследования: **25 сентября 2026**. Первый выпуск реализован и выпускается под флагами по умолчанию off: парсер и чтение рейтингов Sports, привязка Telegram и pipeline отчётов дедлайна. Платные рассылки, отдельный delivery-контейнер и synthetic million load не входят в выпуск; ограничения зафиксированы в TECHDEBT и REVIEW спек.

## Что получится

Пользователь подключает Telegram в настройках профиля и выбирает турниры. В день дедлайна в 08:00 МСК начинается импорт доступного состава Sports, в 08:10 — обновление статистики, коэффициентов и прогнозов основы. С 09:00 бот рассылает отдельный отчёт на каждый турнир/тур: проблемные игроки, бланки, расписание в три столбца, свежесть данных и доступные рейтинги Sports. Теги: `#Англия10`, `#Чемпиошип15`, `#ЛигаЧемпионов3`.

## Что выяснилось

| Вопрос | Проверенный ответ |
|---|---|
| Можно ли парсить популярные покупки Sports? | Да: с production сервера обычным HTTP получены и разобраны 10 покупок и 10 продаж из опубликованной статьи. Регулярность публикаций для всех лиг не доказана. |
| Можно ли получать популярность без статьи? | Да: существующий API и импорт уже получают `selectedBy`. Проверка 15 игроков вернула 15 непустых значений. Это процент выбора, не покупки за тур. |
| Будет ли топ готов в 09:00? | Только если источник опубликовал его до среза. Проверенный пример опубликован в 17:25 в день дедлайна, поэтому утреннему отчёту того дня он был недоступен. |
| Можно ли в 08:00 скачать последние закрытые замены? | Текущий анонимный импорт этого не умеет: открытый состав скрыт до дедлайна. Доступен последний опубликованный состав; свежий состав требует дополнительного канала. |
| Достаточно ли `ALT=0` для «не в старте»? | Нет. Ноль — полезный сигнал, но причину нужно отличать от blank, отсутствия данных и прогноза XI другого матча. |
| Можно ли отправить миллиону ровно в 09:00? | Нет. Теоретический минимум для одного сообщения на человека — 9 ч 15 мин бесплатно либо 16 мин 40 с при paid ceiling, без ошибок и накладных расходов. |
| Сервер проверен фактически? | Да, через SSH alias `deploy`: версия 0.3.85, 8 vCPU, около 11,6 GiB RAM, примерно 5,2 GiB available во время первого замера. |

## Было и предлагается

| Было в проекте | Стало в документации задачи |
|---|---|
| Текущий процент выбора уже сохраняется вместе с ценами; отдельного парсера редакционных топов нет | Описан общий collector до 15 игроков на категорию, source/round/metric validation, дедупликация и отсутствие выдуманного заполнения |
| Нет Telegram-привязки и рассылки | Описаны профильная кнопка, код каждые 15 секунд, подтверждение Telegram identity, consent, пауза и отвязка |
| Автоснимки Sports ориентированы на опубликованные после старта тура составы | Предложен отдельный утренний notification input без перезаписи сохранённых планов; явно указан исходный тур |
| Ночная статистика в 03:00, Sorare каждый час :05, odds по своим триггерам | Описана зависимая цепочка 08:00/08:10/09:00 с проверкой готовности, обновлением ALT, cutoff и честной деградацией |
| Нет формального массового delivery pipeline | Описаны PostgreSQL inbox/outbox, shared snapshots, rate limits, retry/unknown, retention и load gates |

Это изменение документов, а не утверждение, что новые возможности уже работают на сайте.

## Решения, которые нужны до реализации

1. **Свежесть состава.** Рекомендуемый первый выпуск проверяет последний опубликованный Sports состав с видимым указанием тура. Для точных последних замен необходимо добавить согласованный обратный импорт из браузерного расширения или официальный источник. Существующее расширение работает в направлении Scout → Sports, автоматического обратного импорта в 08:00 нет.
2. **Окно доставки и Stars.** На старте малой аудитории — бесплатная очередь. Для миллиона одновременных получателей предлагается paid окно 09:00–09:30 и отдельный бюджет. До принятия бюджета paid выключен. Миллион аккаунтов и миллион адресатов одного утра — разные нагрузки.
3. **Дедлайны до 09:00.** Предлагается отчёт накануне в 09:00 с явной датой. Без такого исключения утреннее уведомление окажется после дедлайна.
4. **Календарь и Sports quota.** До включения лиги нужно подтвердить её настоящий дедлайн и допустимый поток запросов. На сервере scope автоматического Sports sync сейчас покрывает только Россию, Испанию, Нидерланды и Португалию. По некоторым другим лигам обнаружены старые timestamps и срок позже первого матча; использовать это без проверки нельзя.

Эти вопросы записаны как REVIEW. Они не мешают завершить документацию, но влияют на честные обещания готового продукта.

## Последовательность реализации {#implementation}

Ниже разбиение выполненной первой волны; этапы 1–4 реализованы, paid-масштабирование и synthetic load остаются открытыми:

| Этап | Самостоятельный результат | Проверка перед выпуском |
|---|---|---|
| 1. Источники и календарь | Корректные Sports round/deadline для каждой поддерживаемой лиги, parser рейтингов | Реальные fixtures/HTML, неполные и поздние данные, null/zero, отсутствие дублей |
| 2. Привязка Telegram | Пользователь подключается, выбирает турниры и может отключиться | Код/гонки/replay/CSRF, consent, private chat, сохранение текущей авторизации |
| 3. Shadow pipeline | В 08:00/08:10 готовится отчёт без отправки | Источник состава, readiness, target-round ALT, XI нужного матча, три столбца |
| 4. Пилот доставки | Opt-in рассылка малой группе с 09:00 | Rate limits, переносы, restart, unknown delivery, unsubscribe, память и кэш |
| 5. Масштабирование | Подтверждённый объём U×L×P с заданным SLA | Синтетический load, Sports capacity, storage/retention, Telegram paid eligibility и spend cap |

До этапа 1 draft требуется перевести в active после разрешения применимых REVIEW; конкретные implementation WI создаются при поручении реализации. Парсер, привязка и доставка могут выпускаться независимо под флагами.

## Проверка документов

WI-030 учитывает только исследование и authoring. Проверки: источники HTTP, read-only production/БД, регистрация спек, ссылки/anchors, spec snapshot и Git diff. Build и production deploy не требуются, поскольку executable код не менялся. Подтверждения и ограничения проверки зафиксированы в Result WI.
